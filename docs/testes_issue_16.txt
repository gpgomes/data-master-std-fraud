0. BUG REAL ENCONTRADO E CORRIGIDO — Superset nunca funcionou
================================================================================

O servico `superset` do docker-compose.yml nunca subiu corretamente desde
o commit inicial do projeto (nenhuma issue anterior precisou dele de
verdade). Causa raiz: o bloco `command: >` usa YAML folding (`>`), que
colapsa quebras de linha em espaco SO ENTRE linhas na MESMA indentacao da
primeira linha de conteudo — linhas MAIS indentadas (como as flags
`--username admin` do `create-admin`, uma por linha, e `--log-level info
'...'` do gunicorn) preservam a quebra de linha literalmente. Resultado:
  - `superset fab create-admin` rodava SEM nenhuma flag (a quebra de linha
    antes de `--username admin` cortava o comando ali), caindo no prompt
    interativo `Username [admin]:` (travado, sem stdin).
  - `gunicorn --bind ... --keep-alive 5` rodava SEM o modulo da app (a
    quebra de linha antes de `--log-level` cortava o comando ali) ->
    `Error: No application module specified.` -> gunicorn nunca subia de
    fato -> healthcheck perpetuamente `starting`.

Confirmado via `docker compose config --format json` (mostra o array
`command` resolvido) e via `docker compose logs superset` (as duas
mensagens de erro acima, batendo exatamente com a hipotese).

Correcao: cada comando (`create-admin ...`, `gunicorn ...`) colocado numa
UNICA linha logica — sem mudar nenhum valor/flag, so a formatacao YAML.

1. ACHADO REAL — dados que NAO existem para os KPIs "score" e "latencia"
================================================================================

Verificado diretamente no Postgres real (fact_transactions, 506.146
linhas carregadas pela issue #10):

  SELECT COUNT(*) FILTER (WHERE fraud_score IS NOT NULL), COUNT(*)
  FROM fact_transactions;
  -- with_score=0, total=506146

`fraud_score` esta SEMPRE NULL nas 506k linhas — so e populado pelo
detector de streaming (issue #11), que escreve em Kafka
(enriched-transactions/fraud-alerts), nunca na camada Gold batch que
alimenta o Postgres. Mesma causa raiz do gap ja documentado em
`alerts.py` (issue #15): dado streaming-only nunca chega ao Postgres.

Por isso: nenhum chart de distribuicao de `fraud_score` foi construido
(seria sempre vazio); "alertas"/"taxa de fraude" (via `is_fraud`,
`fraud_type`, `fraud_count`/`fraud_rate` de agg_daily_fraud_metrics) sao
os KPIs de fraude realmente disponiveis e sao os usados no dashboard.
"Latencia" de pipeline (ingestion_timestamp/processing_timestamp) tambem
nao chega em fact_transactions/agg_daily_fraud_metrics — mesmo gap,
documentado, fora do escopo desta issue.
