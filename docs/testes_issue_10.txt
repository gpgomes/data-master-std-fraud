CHECKLIST DE TESTES — Loader Gold → PostgreSQL (issue #10)
================================================================================

Objetivo: disponibilizar os dados Gold (star schema) no PostgreSQL da serving
layer, com carga idempotente e sem credenciais hardcoded.

Decisão de arquitetura (confirmada com o usuário): PySpark + JDBC, em vez de
pandas + psycopg2. O job roda dentro do cluster Spark (mesmo padrão dos jobs
bronze_to_silver.py/silver_to_gold.py), lê o Gold via spark.read.parquet e
escreve via spark.write.format("jdbc"). Estratégia de carga: truncate + reload
completo por tabela a cada execução — sempre idempotente, sem upsert real (os
volumes atuais, maior tabela ~500k linhas, não justificam a complexidade extra
de merge via JDBC).

Arquivos criados:
  - src/serving/loaders/gold_to_postgres.py (GoldToPostgresLoader)
  - src/serving/loaders/schema.sql (DDL das 4 tabelas, sem FKs)
  - tests/unit/test_gold_to_postgres.py (11 testes)

Arquivos modificados:
  - docker/spark/Dockerfile (psycopg2-binary + driver JDBC postgresql-42.7.3.jar)
  - Makefile (target spark-submit-gold-postgres)
  - dags/dag_batch_transformation.py (task load_gold_postgres)
  - src/transformation/batch/silver_to_gold.py (bug real encontrado durante o
    teste de integração — ver seção 2)
  - tests/unit/test_silver_to_gold.py (schema/fixture ganharam
    ingestion_timestamp; novo teste de deduplicação)

2. BUG REAL ENCONTRADO E CORRIGIDO DURANTE O TESTE DE INTEGRAÇÃO
================================================================================

A primeira execução real de `make spark-submit-gold-postgres` (dados Gold já
existentes de sessões anteriores) falhou na carga de dim_customers:

  java.sql.BatchUpdateException: ... duplicate key value violates unique
  constraint "dim_customers_pkey"
  Detail: Key (customer_key)=(815ef6d1-...) already exists.

Isso ocorreu na PRIMEIRA carga (tabela recém-truncada) — ou seja, o Gold
Parquet em si já continha customer_key duplicado, algo que só passou a ser
detectado agora porque é a primeira vez que uma PK é imposta sobre
dim_customers (Parquet não tem constraint).

Investigação (query PySpark ad-hoc contra gold/dim_customers/):
  - 71.000 linhas no Gold, mas só 10.000 customer_key distintos.
  - Para um mesmo customer_key, linhas com name/birth_date/segment/
    account_opening_date DIFERENTES — não é duplicata idêntica, são "versões"
    conflitantes do mesmo cliente.

Causa raiz: src/ingestion/batch/customer_loader.py implementa um "SCD Type 2
simplificado" que grava um novo snapshot diário em
bronze/customers/snapshot_date=YYYY-MM-DD/ e marca is_current=True
incondicionalmente em TODAS as linhas — mas nunca fecha (is_current=False) o
snapshot anterior. Como este projeto rodou `make seed-data` em vários dias
diferentes ao longo das últimas semanas (uma vez por sessão/feature), cada dia
deixou um snapshot inteiro "corrente" para sempre. silver_to_gold.py's
_build_dim_customers só filtrava is_current=True, sem deduplicar por
customer_id — os 7+ snapshots acumulados (7 × 10.000 + 1.000 de uma sessão
anterior com --customers diferente = 71.000) passavam direto para o Gold.

Correção aplicada em `src/transformation/batch/silver_to_gold.py`
(_build_dim_customers): após filtrar is_current, deduplica por customer_id
mantendo a linha com o maior ingestion_timestamp (Window + row_number).

Reprocessamento (`make spark-submit-silver-gold --dataset dim_customers`):
  rows_read=71000, rows_discarded=61000, rows_written=10000 — confirma a
  correção: 61.000 linhas de snapshots obsoletos descartadas, sobra 1 por
  cliente.

Teste unitário adicionado (test_silver_to_gold.py):
  test_dedups_multiple_current_snapshots_keeping_latest — dois registros
  is_current=True para o mesmo customer_id com segment diferente e
  ingestion_timestamp diferente → resultado tem 1 linha, com o segment do
  ingestion_timestamp mais recente.

Nota: a causa raiz de fundo (customer_loader.py nunca fecha o snapshot
anterior) não foi alterada — é um gap de design do SCD2 simplificado, fora do
escopo desta issue. A correção aplicada garante a invariante que uma dimensão
Gold exige (unicidade por chave), independente de quem a consome — Postgres
hoje, qualquer outro consumidor (Superset, etc.) amanhã.
