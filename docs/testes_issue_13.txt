================================================================================
CHECKLIST DE TESTES — Quality Gates com Great Expectations (issue #13)
================================================================================

Objetivo: substituir a validação placeholder do Bronze por controles de
qualidade executáveis (Great Expectations) para Bronze, Silver e Gold,
integrados às DAGs do Airflow com política de falha explícita.

Decisão de arquitetura (confirmada com o usuário): gate simples — qualquer
expectativa falhando bloqueia a task do Airflow (e portanto a DAG), sem
quarentena de linhas nem execução parcial. "Quarentena" fica expressa como
trilha de auditoria (data docs + logs da task), não como um dataset separado
de linhas isoladas. Recuperação = corrigir a causa raiz e rerodar a DAG.

Arquivos criados:

    telemetria anônima desabilitada)
  - src/governance/great_expectations/datasets.py (carrega Bronze/Silver/
    Gold do MinIO via pandas — não PySpark)
  - src/governance/great_expectations/suites.py (8 suites, via API Python,
    não YAML/JSON à mão)
  - src/governance/great_expectations/checkpoints.py (1 checkpoint por
    suite, datasource/asset pandas compartilhado)
  - src/governance/great_expectations/runner.py (CLI + `run_gate()`,
    `QualityGateFailed`)
  - src/governance/great_expectations/gx/{expectations,checkpoints}/ +

  - tests/unit/test_great_expectations.py (17 testes — suites completas,

================================================================================
2. BUGS REAIS ENCONTRADOS E CORRIGIDOS DURANTE O TESTE DE INTEGRAÇÃO
================================================================================

A primeira execução real (`runner.py --all` contra o Postgres/MinIO reais)
revelou TRÊS bugs genuínos, nenhum deles hipotético — todos só apareceram
porque essa foi a primeira vez que algo leu Bronze/Silver/Gold inteiros via
pandas (os jobs Spark existentes são mais tolerantes a essas inconsistências,
mascarando-as).

--------------------------------------------------------------------------------
2.1 Colisão de schema em bronze/market_data (ArrowTypeError)
--------------------------------------------------------------------------------
`pd.read_parquet("s3://bronze/market_data/")` falhava:
  ArrowTypeError: Unable to merge: Field date has incompatible types:
  large_string vs dictionary<values=string, indices=int32, ordered=0>

Causa: o único arquivo real (`date=2024-01-02/PETR4.SA.parquet`) tem a
coluna `date` gravada TANTO como partição Hive (nome do diretório) QUANTO
dentro do próprio arquivo — o leitor de dataset particionado do pyarrow tenta
unificar as duas versões (dictionary-encoded da partição vs. string do
arquivo) e falha.

Correção: `datasets.py::load_dataframe` passou a ler cada arquivo Parquet
individualmente pelo caminho completo (não mais apontando para o
diretório), evitando a descoberta de partição Hive do pyarrow por completo,
e concatenando via pandas (mais tolerante a diferenças reais de schema entre
arquivos de ingestões distintas do que a unificação estrita do pyarrow).

--------------------------------------------------------------------------------
2.2 Perda silenciosa de coluna de partição (date_key/date ausentes)
--------------------------------------------------------------------------------
A correção acima, sozinha, introduziu uma REGRESSÃO: `gold/fact_transactions`
e `gold/agg_daily_fraud_metrics` (gravados com `.partitionBy("date_key")`
pelo Spark) e `silver/market_data` (`.partitionBy("date")`) NÃO duplicam a
coluna de partição dentro do arquivo (convenção padrão do Spark) — ler
arquivo a arquivo, sem reconstruir a partição, resultou em `date_key`/`date`
literalmente ausentes do DataFrame carregado (`expect_column_to_exist`
falhando para essas 3 tabelas).

Correção: `_parse_hive_partitions()` extrai pares chave=valor de segmentos
Hive-style no caminho de cada arquivo (`date_key=2024-06-15/` ->
`{"date_key": "2024-06-15"}`) e a coluna é injetada de volta no DataFrame —
mas SÓ quando ainda não existe (preserva o comportamento correto de 2.1,
onde a versão do arquivo é autoritativa quando presente).

--------------------------------------------------------------------------------
2.3 Comparação timezone-naive vs. timezone-aware na checagem de freshness
--------------------------------------------------------------------------------
`silver_transactions` falhava em `expect_column_max_to_be_between` sobre
`processing_timestamp` mesmo com dado genuinamente fresco (verificado:
`processing_timestamp` real = mesma hora da execução). Causa: a coluna vem
como `datetime64[ns]` (sem timezone) do parquet, mas os bounds gerados por
`_freshness()` eram strings ISO COM offset UTC explícito
(`+00:00`) — o GX não compara corretamente naive vs. aware, falhando a
expectativa sem erro explícito (silencioso).

Correção: `_freshness()` gera os bounds sem tzinfo
(`datetime.now(tz=UTC).replace(tzinfo=None)`), batendo com o dtype real dos
dados.

--------------------------------------------------------------------------------
2.4 Telemetria anônima do GX habilitada por padrão
--------------------------------------------------------------------------------
Não é um bug funcional, mas um achado de postura de dados: o GX habilita
`anonymous_usage_statistics.enabled=true` por padrão, enviando dados de uso
para os servidores da própria Great Expectations. Desabilitado
explicitamente em `context.py::get_context()`, consistente com a postura já
estabelecida deste projeto (ex.: issues #8/#9, sem envio de dados
desnecessário a terceiros).
