================================================================================
CHECKLIST DE TESTES — API FastAPI para Consultas e Alertas (issue #15)
================================================================================

Objetivo: implementar a serving API referenciada no README/Makefile —
consultas de transações, KPIs de fraude e alertas recentes sobre o Postgres
carregado pela issue #10, com paginação, filtros, validação de entrada e
health/readiness checks.

Decisões de arquitetura (confirmadas com o usuário):

  1. Fonte de "alertas recentes": `fact_transactions` filtrado por
     `is_fraud=true` (o rótulo de fraude já carregado no Postgres pela issue
     #10, batch). O detector de streaming (issue #11) publica alertas de
     Z-Score no tópico Kafka `fraud-alerts`, mas não os persiste em nenhuma
     tabela consultável hoje — ligar essa fonte real exigiria escrever e
     manter um consumidor Kafka novo, rodando em paralelo à API, fora do
     escopo desta issue (que pede "criar rotas", não um pipeline novo).
     Documentado inline em `src/serving/api/routes/alerts.py` e
     `repository.py`.

  2. Containerização: além de `make api` (host, com --reload, já cobre o
     critério de aceite "make api inicia e /docs está disponível"), foi
     adicionado `docker/api/Dockerfile` + serviço `api` no
     `docker-compose.yml`, atrás de um profile dedicado (`--profile api`) —
     não sobe com `make up` por padrão, mesmo padrão já usado pelos serviços
     `producer-transactions`/`producer-market`. Resolve o Postgres via
     `POSTGRES_HOST=postgres` (override de ambiente no serviço), enquanto o
     host usa `POSTGRES_HOST=localhost` do `.env` — sem duplicar lógica de
     conexão.

Arquivos criados:
  - src/serving/api/db.py (engine SQLAlchemy + dependency get_db)
  - src/serving/api/models/schemas.py (Page[T], PaginationParams,
    TransactionOut, DailyFraudMetricOut)
  - src/serving/api/repository.py (SQL parametrizado — sem interpolação de
    string — contra fact_transactions/agg_daily_fraud_metrics)
  - src/serving/api/routes/{health,transactions,alerts,kpis}.py
  - src/serving/api/main.py
  - docker/api/Dockerfile
  - tests/unit/test_api.py (29 testes)

Arquivos modificados:
  - docker-compose.yml (serviço `api`, profile dedicado)
  - .env.example (API_EXTERNAL_PORT=8000, mesmo padrão de
    MINIO_EXTERNAL_PORT/POSTGRES_EXTERNAL_PORT)

1. TESTES UNITÁRIOS — tests/unit/test_api.py
================================================================================

Comando:
  pytest tests/unit/test_api.py -v

Resultado: 29/29 PASSED.

Estratégia: `repository.py` é testado contra SQLite in-memory (SQL real
executado, não mocks — mesmo espírito dos testes com PySpark local do resto
do projeto). As rotas são testadas via `TestClient` do FastAPI +
`dependency_overrides` trocando `get_db` pela sessão SQLite; a falha de banco
é simulada com uma sessão fake cujo `.execute()` levanta `OperationalError`
(não fazendo a PRÓPRIA dependência falhar — isso simularia um cenário
diferente do que o código realmente trata, já que uma Session do SQLAlchemy
não abre conexão de fato até a primeira query).
